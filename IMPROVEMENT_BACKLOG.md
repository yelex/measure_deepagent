## [L001] LLM-экстрактор: фикс grounding bug

- Статус: done
- Приоритет: high
- Источник: B008 revert (итерация 1, 2026-08-11). Предполагалось: GLM-5 возвращает корректные цитаты через structured output, но `_quote_grounded` в v2 проверяет их против текста, который НЕ совпадает с тем что видела модель.
- **Реальная причина (найдена 2026-08-11, itr. 2)**: гипотеза про text mismatch была НЕВЕРНА — текст идентичен в обоих местах. Настоящий баг — в парсинге ответа GLM: для полей со вложенной $ref-схемой (`FieldExtraction {value, quote}`) GLM возвращает значение как **JSON-строку** (`"{\"value\": ..., \"quote\": ...}"`), а не нативный вложенный объект. `extract_measure_via_llm` проверял только `isinstance(entry, dict)` / `isinstance(entry, FieldExtraction)` — `str`-значения проваливались в `else: value=None, quote=None`. Именно это обнуляло ВСЕ поля, а не отклонение по grounding.
- Фикс: добавлена ветка `isinstance(entry, str)` → `json.loads(entry)` перед проверкой на dict (с fallback на `None` при ошибке парсинга). См. `revision_agent/llm_extract_v2.py::extract_measure_via_llm`.
- Проверка: e2e-тест на `77_vbd_4` (аэроэкспресс, тот же кейс что был fully-null в attempt B008) — карточка получила 3 заполненных поля (`categoryOfVeteran`, `measureTerms`, `department`), 2 корректно null (`measureSum`, `measurePeriodicity` — не упомянуты в тексте источника). Критерий успеха (≥3 заполненных поля) выполнен.
- Eval: `score_against_golden.py` в этой итерации НЕ запускался — нет валидного LLM-агрегированного `agent_cards_export.json` (батч-прогон = L002, ещё не сделан). Прогон scorer'а на старом regex-экспорте был бы бессмысленным шумом в tuning_log (никак не отражает эту правку). Полноценный score-based eval начнётся с L002.
- Побочная находка (НЕ фиксилась в этой итерации, см. L006): boolean-коэрсия `if fname.startswith("category")` в `extract_measure_via_llm` неверно применяется к `categoryOfVeteran` (ЖС "вбд") — это ТЕКСТОВОЕ поле (категория ветерана), а не булево, но код превращает любую непустую строку в `1`, теряя реальное значение. Баг актуален только для "category*"-полей ЖС "вбд" (для "сво" `category*` действительно булевы).

     ключевые слова сравниваются по стему (первые 6 симв.) и перебираются
     от самого длинного/специфичного слова, беря первое совпадение

## [L007] Эксперимент: Swarm-архитектура для LLM-экстрактора

- Статус: todo
- Приоритет: medium
- Источник: L002-L003. Текущий LLM-экстрактор — это один агент, который пытается извлечь все поля за один вызов. Для разных ЖС (вбд/сво/инвалиды) и разных типов полей (текстовые/булевы/даты/суммы) нужны разные стратегии. Один промпт не может быть оптимальным для всех.
- Гипотеза: Swarm из специализированных субагентов (по одному на ЖС + отдельный валидатор) даст AvgQS ≥ 0.35 на L002-датасете (против 0.248 у монолитного агента), за счёт:
  1. Специализации промптов: каждый агент получает инструкцию, оптимизированную под свою схему и типы полей (агент для "вбд" умеет работать с текстовым categoryOfVeteran, агент для "инвалидов" — с cause_* булевыми полями).
  2. Изоляции контекста: субагенты не путают поля разных схем (текущий баг L006 — прямая иллюстрация).
  3. Валидации через субагента-чекера: отдельный агент проверяет цитаты на groundedness (исправляет L001-style ошибки на уровне пост-обработки) и конфликтует, если цитаты не совпадают с текстом.
  4. Возможности handoff: если агент "вбд" не уверен в поле, он может передать запрос агенту-валидатору или агенту "общий" с более широким контекстом.
- Архитектура (предварительная):
  - Main coordinator (без инструментов) → определяет ЖС по URL или тексту, передаёт запрос в соответствующего субагента через task().
  - Subagent: vbd_extractor → извлекает поля для ВБД (categoryOfVeteran — текст, measureTerms, department, measureSum, measurePeriodicity). Промпт явно указывает: categoryOfVeteran — ЭТО ТЕКСТ, НЕ БУЛЕВО.
  - Subagent: svo_extractor → извлекает булевы поля (categoryMobilized, categoryContractor, categoryVolunteer) + measureTerms, department.
  - Subagent: invalid_extractor → извлекает поля для инвалидов (cause_* булевы) + общие поля.
  - Subagent: grounding_validator → получает извлечённые поля и проверяет каждую цитату на наличие в исходном тексте; если цитата отсутствует → помечает поле как null (fallback). Может запросить повторную экстракцию у специализированного агента.
- Действие:
  1. Создать прототип в revision_agent/swarm_extractor.py с использованием deepagents (координатор + субагенты через task()).
  2. Запустить на subset'е (по 5 карточек на ЖС) вручную, проверить качество экстракции.
  3. Если качество выше монолитного — запустить полный batch (43 карточки), сравнить с L002-результатами.
  4. Замерить latency (swarm может быть медленнее из-за нескольких LLM-вызовов) — если >30с на карточку, искать компромисс.
- Критерий успеха:
  - Основной: AvgQS ≥ 0.35 на полном датасете (прирост от 0.248).
  - Дополнительный: 100%-е исправление L006 (текстовое categoryOfVeteran не коэрсится).
  - Допустимый порог latency: ≤20с на карточку (против текущих ~5с у монолитного) — если больше, считать эксперимент неудачным для production, но документировать как research-результат.
- Зависимости:
  - L003 (сравнение с regex и монолитный LLM — нужно для baseline).
  - L006 (фикс булевой коэрсии — если не починить, swarm с вбд-агентом всё равно будет наступать на те же грабли).
- Потенциальные риски:
  - Сложность отладки (4 субагента vs 1).
  - Увеличение стоимости (4-5 вызовов GLM вместо 1).
  - Если GLM-5 плохо понимает ручной handoff — возможно, координатор будет "перекладывать" запросы бесконечно.
  - Нет гарантии, что субагенты не дублируют работу (overhead).
- Решение в случае неудачи: свернуться на монолитного агента с улучшенным промптом (few-shot), но архитектурный опыт задокументировать.

cntd.ru**, как заявлено в названии задачи L011 ("для cntd.ru"), а
применяется ко ВСЕМ источникам всех ЖС без разбора. Для документов,
которые физически посвящены ОДНОЙ конкретной мере (частый случай для
"сво"/"инвалиды" — см. `docs/Обработка НПА` п.1.2, "документ описывает
предоставление одной конкретной меры"), ключевое слово упоминается в
заголовке/преамбуле (позиция < 3000) и не повторяется дальше по
короткому тексту — функция ошибочно считает полностью релевантный,
корректно загруженный документ "не относящимся к теме" и форсирует
fallback на `search_and_fetch_npa` (L008), которого раньше не было. При
батч-прогоне по 43 seed'ам это резко увеличило число вызовов Yandex
Search API; к моменту обработки ЖС "инвалиды" (третьим и последним по
порядку в реестре) поиск, похоже, перестал возвращать пригодный текст
(квота/рейт-лимит/деградация), и функция стала писать пустые карточки
почти для всех оставшихся мер.

**Рекомендация следующему Coder-проходу** (приоритет critical, впереди
любого prompt-tuning): либо (а) ограничить `no_relevant_content`-триггер
доменом cntd.ru, как изначально задумано в L011, либо (б) исправить саму
эвристику `has_relevant_content` — не наказывать документы, где ключевое
слово встречается только в первых 3000 символах, если больше в тексте
источника ничего релевантного другой мере тоже нет (то есть текст короткий
и посвящён этой мере целиком). Перед повторным batch-прогоном стоит
проверить `search_and_fetch_npa` на предмет отсутствия retry/backoff при
ошибках квоты — если каждый неудачный вызов молча проглатывается и
переходит в пустую карточку, лучше не расширять его использование, пока
это не исправлено. **Обязательно довести Coder-проход до записи
`ralph_handoff.json`, чтобы Tester реально проверил результат** — не
повторять паттерн двух "оборванных" итераций.

### [ANALYST 2026-08-13, второй проход] Коррекция root-cause: это НЕ Yandex Search quota, это GLM rate-limit

Разбор выше (запись сразу над этой) объяснил каскад пустых карточек
"инвалиды"/"сво" исчерпанием квоты **Yandex Search API** через
избыточные вызовы `search_and_fetch_npa` (L008). Это объяснение
правдоподобно выглядело по косвенным признакам (порядок деградации
совпадает с порядком ЖС в реестре), но **прямая проверка исходных логов
опровергает его**.

`data/output/tmp_llm_run.log` (18010 симв., тот же прогон, что
породил регрессивный `agent_cards_export.json` от 2026-08-12 23:15 —
совпадают timestamps файлов) содержит для каждой карточки, начиная
примерно с середины ЖС "сво" и до самого конца ЖС "инвалиды" (35 из
131 строк лога), буквально:
```
ОШИБКА LLM: HTTP 429: {"error":{"code":"1308","message":"Usage limit
reached for 5 hour. Your limit will reset at 2026-08-13 07:32:48"}}
0/0 полей заполнено
```
Это ответ от **GLM** (`revision_agent/llm_extract_v2.py::_call_glm_structured`),
не от Yandex Search. Проверка `revision_agent/npa_fetcher.py` (grep на
`llm|glm|api`) подтверждает: этот модуль вообще не делает вызовов LLM —
только HTTP-fetch/поиск. Значит избыточные вызовы `search_and_fetch_npa`
от неправильно широкого триггера L011 **не могли** быть причиной этого
конкретного отказа — они увеличивают нагрузку на Yandex Search API, а
не на GLM. `_call_glm_structured` действительно вызывается ровно один
раз на карточку (43 карточки = 43 вызова GLM за прогон), и как только
пятичасовое окно использования GLM исчерпалось (видимо, из-за суммарной
нагрузки нескольких ручных/тестовых прогонов в течение дня плюс сам
этот batch), **все последующие карточки без исключения** стали
получать 429 — независимо от домена источника, от того, сработал ли
`has_relevant_content`, и от того, чинить ли L011 доменным скоупом или
как-то иначе. Это структурно объясняет и асимметрию по ЖС (порядок
реестра вбд→сво→инвалиды точно определяет, какие карточки успели
обработаться до исчерпания окна, а какие — нет) без всякой связи с
кодом L011.

**Практическое следствие**: доменный фикс `7baa898` (см. новый статус
задачи выше) — легитимное сужение `no_relevant_content` до cntd.ru,
как и было задумано изначально, стоит оставить. Но он **не защищает от
повторения катастрофы** — если пятичасовое окно GLM исчерпается
партway через любой будущий batch-прогон (в том числе прогон,
подтверждающий сам этот фикс), пайплайн снова молча запишет
carточки-заглушки для всех оставшихся мер, потому что `_call_glm_structured`
в этом случае просто исчерпывает 2 ретрая по 3 секунды (бесполезно
против пятичасового окна) и возвращает `None`-поля, а вызывающий код
не отличает "квота кончилась" от любой другой временной ошибки. См.
новую задачу [L013] — она должна быть закрыта (или как минимум учтена
Coder-проходом при следующем batch-прогоне: проверить `tmp_llm_run.log`/
stdout на `HTTP 429` и `Usage limit` ПОСЛЕ прогона, прежде чем доверять
экспорту) до того, как результат L011-domain-scope фикса можно будет
считать надёжно подтверждённым.

## [L013] Обработка исчерпания квоты/rate-limit GLM в батч-пайплайне

- Статус: done
- Приоритет: **critical** — без этого фикса любой batch-прогон (включая
  верификацию L011-фикса) может молча превратиться в десятки
  карточек-заглушек, если пятичасовое окно использования GLM
  исчерпается посреди прогона; это делает eval-результаты недостоверными
  ровно тогда, когда они больше всего нужны (после code-фикса).
- Источник: прямой лог `data/output/tmp_llm_run.log` от прогона
  2026-08-12 23:15 — 35 подряд ошибок `HTTP 429: Usage limit reached
  for 5 hour` начиная с середины ЖС "сво" до конца "инвалиды" (см.
  разбор в L011 выше, "Коррекция root-cause").
- Проблема: `_call_glm_structured` (`revision_agent/llm_extract_v2.py`)
  делает 2 ретрая с фиксированной паузой 3с при ЛЮБОЙ HTTP-ошибке,
  включая 429 с пятичасовым окном — ретраи гарантированно бесполезны в
  этом случае, а после их исчерпания карточка тихо становится
  `{measureId, region, measureName}`-заглушкой, неотличимой от
  `too_short`/`no_relevant_content` fallback по данным экспорта. Это
  скрывает реальную причину провала и корректирует Recall/AvgQS вниз
  так, что это легко перепутать с регрессией экстрактора (как и
  произошло в предыдущем Analyst-проходе).
- Действие (план):
  1. В `_call_glm_structured` различать `HTTP 429` с телом, содержащим
     `"Usage limit"`/`"code":"1308"` (пятичасовое окно — retry
     бессмысленен) от прочих временных ошибок (тут retry уместен).
  2. При обнаружении quota-исчерпания — не ретраить бесполезно, а
     поднять специфичное исключение/статус, которое `run_llm_mode`
     (`scripts/run_pipeline_demo.py`) должен трактовать как сигнал
     остановить весь оставшийся batch (не писать заглушки для всех
     оставшихся карточек), с понятным сообщением в консоль/лог и явным
     ненулевым кодом возврата.
  3. Опционально: записывать количество quota-ошибок в сам экспорт или
     в отдельный маркер-файл, чтобы Tester мог автоматически отличить
     "полноценный прогон с плохими метриками" от "прогон, оборванный
     квотой" ещё до ручного грепа логов.
- Критерий успеха: тестовый прогон, вручную имитирующий 429 после N-й
  карточки (или следующий реальный прогон, если окно снова
  исчерпается), не производит карточки-заглушки для необработанных
  мер — batch останавливается с явной ошибкой вместо тихой порчи
  экспорта.
- Зависимости: нет технических; логически блокирует надёжную
  верификацию [L011] и любых будущих batch-прогонов.
