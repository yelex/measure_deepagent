# IMPROVEMENT_BACKLOG.md

Единственный источник правды о том, что делать следующей итерации Ralph
loop. Обновляется только агентом (в рамках итерации) или человеком вручную
между запусками. Статусы: `todo` / `in_progress` / `blocked` / `done` /
`reverted`.

Формат записи:

```
## [ID] Краткое название
- Статус: todo
- Приоритет: high | medium | low
- Источник: откуда взялась задача (конкретная запись в tuning_log / review_queue / ручное наблюдение человека)
- Гипотеза: что должно улучшиться и почему
- История: (заполняется агентом по мере попыток — что пробовали, что не сработало)
```

  просто "не помогло", а недоступно в принципе в рамках автономной
  сессии. Pure-Python шim вместо `pyexpat` признан нецелесообразным (см.
  разбор в трейс-файле) — `ElementTree`/`openpyxl` требуют полноценный
  потоковый C-парсер, а не тонкую обёртку. Код не менялся, eval не
  прогонялся (недоступен), commit/revert не применимы. Полный разбор:
  `data/output/ralph_iteration_20260801_171211.md`.
- История: **2026-08-01, ручная диагностика** — обе автономные итерации
  проверяли только Homebrew-сборки Python (3.11/3.12/3.14), у всех трёх
  сломан `pyexpat`. Но на этой машине отдельно стоит `pyenv` с python
  3.12.0, у которого `openpyxl` работает нормально (не переустанавливали
  специально — он уже был). Проблема не в Python как таковом, а в том,
  что `pyenv shims` не всегда попадают в PATH автономной Bash-сессии,
  поэтому голый `python3`/`python3 -m venv .venv` резолвится в сломанный
  Homebrew-python. Рабочий обход, не требующий системных изменений:
  `pyenv exec python3 ...` — явно резолвит pyenv-интерпретатор в обход
  PATH-неопределённости. Проверено вживую в отдельном `claude -p`
  процессе (не просто в этой интерактивной сессии): `pyenv exec python3
  -c "import openpyxl"` и полный прогон
  `pyenv exec python3 scripts/score_against_golden.py ...` — оба
  отработали без ошибок, denials пустой. Добавлено
  `Bash(pyenv*)` в `.claude/settings.json` (permissions.allow), обновлены
  `RALPH_PROMPT.md` (шаг 4) и `AGENTS.md` на `pyenv exec python3` вместо
  `.venv/bin/python`/голого `python3`. Задача закрыта — если проблема
  всплывёт снова на другой машине/образе, где `pyenv` тоже не настроен,
  заводить новую задачу, не переоткрывать эту.
