## [L001] LLM-экстрактор: фикс grounding bug

- Статус: done
- Приоритет: high
- Источник: B008 revert (итерация 1, 2026-08-11). Предполагалось: GLM-5 возвращает корректные цитаты через structured output, но `_quote_grounded` в v2 проверяет их против текста, который НЕ совпадает с тем что видела модель.
- **Реальная причина (найдена 2026-08-11, itr. 2)**: гипотеза про text mismatch была НЕВЕРНА — текст идентичен в обоих местах. Настоящий баг — в парсинге ответа GLM: для полей со вложенной $ref-схемой (`FieldExtraction {value, quote}`) GLM возвращает значение как **JSON-строку** (`"{\"value\": ..., \"quote\": ...}"`), а не нативный вложенный объект. `extract_measure_via_llm` проверял только `isinstance(entry, dict)` / `isinstance(entry, FieldExtraction)` — `str`-значения проваливались в `else: value=None, quote=None`. Именно это обнуляло ВСЕ поля, а не отклонение по grounding.
- Фикс: добавлена ветка `isinstance(entry, str)` → `json.loads(entry)` перед проверкой на dict (с fallback на `None` при ошибке парсинга). См. `revision_agent/llm_extract_v2.py::extract_measure_via_llm`.
- Проверка: e2e-тест на `77_vbd_4` (аэроэкспресс, тот же кейс что был fully-null в attempt B008) — карточка получила 3 заполненных поля (`categoryOfVeteran`, `measureTerms`, `department`), 2 корректно null (`measureSum`, `measurePeriodicity` — не упомянуты в тексте источника). Критерий успеха (≥3 заполненных поля) выполнен.
- Eval: `score_against_golden.py` в этой итерации НЕ запускался — нет валидного LLM-агрегированного `agent_cards_export.json` (батч-прогон = L002, ещё не сделан). Прогон scorer'а на старом regex-экспорте был бы бессмысленным шумом в tuning_log (никак не отражает эту правку). Полноценный score-based eval начнётся с L002.
- Побочная находка (НЕ фиксилась в этой итерации, см. L006): boolean-коэрсия `if fname.startswith("category")` в `extract_measure_via_llm` неверно применяется к `categoryOfVeteran` (ЖС "вбд") — это ТЕКСТОВОЕ поле (категория ветерана), а не булево, но код превращает любую непустую строку в `1`, теряя реальное значение. Баг актуален только для "category*"-полей ЖС "вбд" (для "сво" `category*` действительно булевы).

## [L006] LLM-экстрактор: боковая коэрсия ломает текстовое поле categoryOfVeteran

- Статус: todo
- Приоритет: medium
- Источник: побочная находка при L001 (2026-08-11, itr. 2). В `extract_measure_via_llm` булева нормализация `if fname.startswith("category") or fname.startswith("cause") or fname.startswith("kids"): card[fname] = int(value) if str(value) in ("0","1","0.0","1.0") else (1 if value else 0)` рассчитана на булевы поля ЖС "сво" (`categoryMobilized`/`categoryContractor`/`categoryVolunteer`) и "инвалиды" (`cause_*`), но по префиксу `"category"` ошибочно ловит и `categoryOfVeteran` ЖС "вбд" — это ТЕКСТОВОЕ поле ("категория получателя (текст)", см. `_build_extraction_schema`). Любое непустое текстовое значение превращается в `1`, реальный текст теряется.
- Подтверждено вручную: e2e-тест на `77_vbd_4` дал `categoryOfVeteran: 1` вместо текста категории ветерана из цитаты.
- Гипотеза: нужно различать булевы и текстовые поля не по префиксу имени, а по явному списку (или отдельному полю схемы), специфичному для каждой ЖС — вбд не должен коэрситься.
- Действие: заменить startswith-эвристику на явную карту `BOOLEAN_FIELDS = {"сво": [...], "инвалиды": [...]}` (для "вбд" — пустой список), использовать её вместо `fname.startswith(...)`.
- Критерий успеха: `77_vbd_4` даёт `categoryOfVeteran` = текст цитаты, не `1`/`0`.

## [L007] Эксперимент: Swarm-архитектура для LLM-экстрактора

- Статус: todo
- Приоритет: medium
- Источник: L002-L003. Текущий LLM-экстрактор — это один агент, который пытается извлечь все поля за один вызов. Для разных ЖС (вбд/сво/инвалиды) и разных типов полей (текстовые/булевы/даты/суммы) нужны разные стратегии. Один промпт не может быть оптимальным для всех.
- Гипотеза: Swarm из специализированных субагентов (по одному на ЖС + отдельный валидатор) даст AvgQS ≥ 0.35 на L002-датасете (против 0.248 у монолитного агента), за счёт:
  1. Специализации промптов: каждый агент получает инструкцию, оптимизированную под свою схему и типы полей (агент для "вбд" умеет работать с текстовым categoryOfVeteran, агент для "инвалидов" — с cause_* булевыми полями).
  2. Изоляции контекста: субагенты не путают поля разных схем (текущий баг L006 — прямая иллюстрация).
  3. Валидации через субагента-чекера: отдельный агент проверяет цитаты на groundedness (исправляет L001-style ошибки на уровне пост-обработки) и конфликтует, если цитаты не совпадают с текстом.
  4. Возможности handoff: если агент "вбд" не уверен в поле, он может передать запрос агенту-валидатору или агенту "общий" с более широким контекстом.
- Архитектура (предварительная):
  - Main coordinator (без инструментов) → определяет ЖС по URL или тексту, передаёт запрос в соответствующего субагента через task().
  - Subagent: vbd_extractor → извлекает поля для ВБД (categoryOfVeteran — текст, measureTerms, department, measureSum, measurePeriodicity). Промпт явно указывает: categoryOfVeteran — ЭТО ТЕКСТ, НЕ БУЛЕВО.
  - Subagent: svo_extractor → извлекает булевы поля (categoryMobilized, categoryContractor, categoryVolunteer) + measureTerms, department.
  - Subagent: invalid_extractor → извлекает поля для инвалидов (cause_* булевы) + общие поля.
  - Subagent: grounding_validator → получает извлечённые поля и проверяет каждую цитату на наличие в исходном тексте; если цитата отсутствует → помечает поле как null (fallback). Может запросить повторную экстракцию у специализированного агента.
- Действие:
  1. Создать прототип в revision_agent/swarm_extractor.py с использованием deepagents (координатор + субагенты через task()).
  2. Запустить на subset'е (по 5 карточек на ЖС) вручную, проверить качество экстракции.
  3. Если качество выше монолитного — запустить полный batch (43 карточки), сравнить с L002-результатами.
  4. Замерить latency (swarm может быть медленнее из-за нескольких LLM-вызовов) — если >30с на карточку, искать компромисс.
- Критерий успеха:
  - Основной: AvgQS ≥ 0.35 на полном датасете (прирост от 0.248).
  - Дополнительный: 100%-е исправление L006 (текстовое categoryOfVeteran не коэрсится).
  - Допустимый порог latency: ≤20с на карточку (против текущих ~5с у монолитного) — если больше, считать эксперимент неудачным для production, но документировать как research-результат.
- Зависимости:
  - L003 (сравнение с regex и монолитный LLM — нужно для baseline).
  - L006 (фикс булевой коэрсии — если не починить, swarm с вбд-агентом всё равно будет наступать на те же грабли).
- Потенциальные риски:
  - Сложность отладки (4 субагента vs 1).
  - Увеличение стоимости (4-5 вызовов GLM вместо 1).
  - Если GLM-5 плохо понимает ручной handoff — возможно, координатор будет "перекладывать" запросы бесконечно.
  - Нет гарантии, что субагенты не дублируют работу (overhead).
- Решение в случае неудачи: свернуться на монолитного агента с улучшенным промптом (few-shot), но архитектурный опыт задокументировать.
