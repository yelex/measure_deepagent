## [L001] LLM-экстрактор: фикс grounding bug

- Статус: done
- Приоритет: high
- Источник: B008 revert (итерация 1, 2026-08-11). Предполагалось: GLM-5 возвращает корректные цитаты через structured output, но `_quote_grounded` в v2 проверяет их против текста, который НЕ совпадает с тем что видела модель.
- **Реальная причина (найдена 2026-08-11, itr. 2)**: гипотеза про text mismatch была НЕВЕРНА — текст идентичен в обоих местах. Настоящий баг — в парсинге ответа GLM: для полей со вложенной $ref-схемой (`FieldExtraction {value, quote}`) GLM возвращает значение как **JSON-строку** (`"{\"value\": ..., \"quote\": ...}"`), а не нативный вложенный объект. `extract_measure_via_llm` проверял только `isinstance(entry, dict)` / `isinstance(entry, FieldExtraction)` — `str`-значения проваливались в `else: value=None, quote=None`. Именно это обнуляло ВСЕ поля, а не отклонение по grounding.
- Фикс: добавлена ветка `isinstance(entry, str)` → `json.loads(entry)` перед проверкой на dict (с fallback на `None` при ошибке парсинга). См. `revision_agent/llm_extract_v2.py::extract_measure_via_llm`.
- Проверка: e2e-тест на `77_vbd_4` (аэроэкспресс, тот же кейс что был fully-null в attempt B008) — карточка получила 3 заполненных поля (`categoryOfVeteran`, `measureTerms`, `department`), 2 корректно null (`measureSum`, `measurePeriodicity` — не упомянуты в тексте источника). Критерий успеха (≥3 заполненных поля) выполнен.
- Eval: `score_against_golden.py` в этой итерации НЕ запускался — нет валидного LLM-агрегированного `agent_cards_export.json` (батч-прогон = L002, ещё не сделан). Прогон scorer'а на старом regex-экспорте был бы бессмысленным шумом в tuning_log (никак не отражает эту правку). Полноценный score-based eval начнётся с L002.
- Побочная находка (НЕ фиксилась в этой итерации, см. L006): boolean-коэрсия `if fname.startswith("category")` в `extract_measure_via_llm` неверно применяется к `categoryOfVeteran` (ЖС "вбд") — это ТЕКСТОВОЕ поле (категория ветерана), а не булево, но код превращает любую непустую строку в `1`, теряя реальное значение. Баг актуален только для "category*"-полей ЖС "вбд" (для "сво" `category*` действительно булевы).

## [L006] LLM-экстрактор: боковая коэрсия ломает текстовое поле categoryOfVeteran

- Статус: todo
- Приоритет: medium
- Источник: побочная находка при L001 (2026-08-11, itr. 2). В `extract_measure_via_llm` булева нормализация `if fname.startswith("category") or fname.startswith("cause") or fname.startswith("kids"): card[fname] = int(value) if str(value) in ("0","1","0.0","1.0") else (1 if value else 0)` рассчитана на булевы поля ЖС "сво" (`categoryMobilized`/`categoryContractor`/`categoryVolunteer`) и "инвалиды" (`cause_*`), но по префиксу `"category"` ошибочно ловит и `categoryOfVeteran` ЖС "вбд" — это ТЕКСТОВОЕ поле ("категория получателя (текст)", см. `_build_extraction_schema`). Любое непустое текстовое значение превращается в `1`, реальный текст теряется.
- Подтверждено вручную: e2e-тест на `77_vbd_4` дал `categoryOfVeteran: 1` вместо текста категории ветерана из цитаты.
- Гипотеза: нужно различать булевы и текстовые поля не по префиксу имени, а по явному списку (или отдельному полю схемы), специфичному для каждой ЖС — вбд не должен коэрситься.
- Действие: заменить startswith-эвристику на явную карту `BOOLEAN_FIELDS = {"сво": [...], "инвалиды": [...]}` (для "вбд" — пустой список), использовать её вместо `fname.startswith(...)`.
- Критерий успеха: `77_vbd_4` даёт `categoryOfVeteran` = текст цитаты, не `1`/`0`.
