## Диагностика (до правки)

Гипотеза из backlog была: text mismatch между тем, что видит модель
(`_cut_to_relevant` в `extract_measure_via_llm`) и тем, что проверяет
`_quote_grounded` (другое представление текста).

Проверка: реальный e2e-вызов на `77_vbd_4` (аэроэкспресс,
`aeroexpress.ru/aero/info/benefits.html`, тот же кейс что был в
предыдущей (пре-reset) попытке B008, где "grounding rejected all
fields"). GLM API доступен (квота не исчерпана). Добавлено raw-response
logging перед grounding-фильтром (диагностика, не в проде).

**Найдена реальная причина** — не text mismatch, а баг типов:
GLM возвращает вложенные `$ref`-поля схемы (`FieldExtraction {value,
quote}`) как JSON-**строку** (`"{\"value\": ..., \"quote\": ...}"`),
а не как нативный JSON-объект. Raw response показывает это явно:
`"department": "{\"value\": \"Аэроэкспресс\", \"quote\": \"...\"}"`
(тип str, а не dict).

`extract_measure_via_llm` в текущем коде обрабатывает только
`isinstance(entry, dict)` и `isinstance(entry, FieldExtraction)` —
`str`-значения проваливаются в `else: value=None, quote=None`. Именно
поэтому ВСЕ поля стабильно уходили в null: не из-за того что цитаты не
граундятся в тексте, а потому что value/quote вообще не извлекались из
ответа модели.

Проверка вручную: если распарсить эти JSON-строки (`json.loads(entry)`)
и прогнать `_quote_grounded` против того же `clean_texts`, что видела
модель — 3 из 5 полей вбд-карточки аэроэкспресса граундятся успешно
(`categoryOfVeteran`, `measureTerms`, `department`), 2 корректно остаются
null (`measureSum`, `measurePeriodicity` — мера неденежная, периодичность
не указана в тексте). Text mismatch гипотеза из backlog была неверна —
тексты идентичны, баг был в парсинге ответа.

## Гипотеза
Если добавить обработку `str`-значений в цикле сборки карточки
(`json.loads(entry)` перед проверкой на `value`/`quote`) — LLM-карточка
перестанет быть fully-null и получит ≥3 заполненных полей на тестовом
кейсе.

## План проверки
1. Править `extract_measure_via_llm`: добавить ветку `isinstance(entry, str)`
   → `json.loads`, с fallback на `None`/`None` при ошибке парсинга.
2. Прогнать `extract_measure_via_llm` на `77_vbd_4` напрямую (без полного
   pipeline — `run_pipeline_demo.py --llm-mode` ещё не существует, это
   L002) и убедиться что карточка не fully-null (критерий L001).
3. `score_against_golden.py` не запускается в этой итерации на полном
   прогоне — LLM ещё не подключён к `run_pipeline_demo.py` (L002,
   отдельная задача). Проверка ограничена критерием успеха L001:
   "LLM-карточка имеет ≥3 заполненных полей".

## Результат

Правка внесена в `revision_agent/llm_extract_v2.py::extract_measure_via_llm`:
перед проверкой `isinstance(entry, dict)` добавлена ветка
`isinstance(entry, str) → json.loads(entry)` (fallback на `None` при
`JSONDecodeError`).

E2e-тест на `77_vbd_4` (аэроэкспресс) ДО правки:
```json
{"categoryOfVeteran": null, "measureSum": null, "measurePeriodicity": null,
 "measureTerms": null, "department": null}
```
(0 заполненных полей — тот же fully-null результат, что и в старой,
пре-reset попытке B008).

ПОСЛЕ правки:
```json
{"categoryOfVeteran": 1, "measureSum": null, "measurePeriodicity": null,
 "measureTerms": "Для проезда необходимо оформить безденежный проездной документ",
 "department": "Аэроэкспресс"}
```
3 заполненных поля (`categoryOfVeteran`, `measureTerms`, `department`),
2 корректно null (мера неденежная, периодичность не упомянута). Критерий
успеха L001 (≥3 заполненных поля) — выполнен.

Замечено: `categoryOfVeteran` = `1` вместо ожидаемого текста категории —
это отдельный баг (boolean-коэрсия по startswith("category") ловит
текстовое поле вбд), зафиксирован как новая задача L006, НЕ исправлялся
в этой итерации (вне скоупа L001, отдельное изменение).

Score-based eval (`score_against_golden.py`) не запускался — нет batch
LLM-экспорта (`run_pipeline_demo.py` не поддерживает LLM-режим, это
L002, следующая задача по приоритету). Прогон scorer'а на устаревшем
regex-экспорте не отразил бы эту правку и был бы шумом в tuning_log.
