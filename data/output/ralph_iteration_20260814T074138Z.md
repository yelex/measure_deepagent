## Гипотеза

Дважды за 2026-08-14 наблюдались одновременные запуски `ralph_loop.sh`
(см. backlog L016/L017: два Coder-процесса правили один файл, два
Tester-процесса гонялись за одним `ralph_handoff.json`, `tuning_log.jsonl`
получил дублирующие записи для одного и того же коммита). Причина —
отсутствие взаимного исключения между запусками скрипта: ничто не мешает
второй копии `ralph_loop.sh` стартовать, пока первая ещё работает.

Фикс: обернуть весь скрипт в `flock`-лок (advisory file lock через
файловый дескриптор) на lock-файле в `data/output/ralph_runs/` —
не просто touch-файл (тот может "зависнуть" навсегда, если процесс
упадёт без очистки), а `flock`, который автоматически освобождается
ядром при завершении процесса-держателя (даже при крахе/kill -9), что
снимает риск "мёртвого" лока, явно отмеченный в backlog как опасность
наивной реализации.

## План проверки

1. Добавить `exec 200>"$LOCK_FILE"; flock -n 200 || { echo ...; exit 1; }`
   в начало `ralph_loop.sh` (non-blocking — второй запуск сразу выходит
   с понятным сообщением, не блокируется в очереди — так проще
   диагностировать проблему по логам, чем зависший процесс).
2. Ручная проверка: запустить `bash ralph_loop.sh` с `MAX_ITERATIONS=0`
   (или coreutils-эквивалент) дважды подряд в одном терминале — второй
   запуск должен немедленно завершиться с сообщением "уже выполняется",
   не пытаясь запустить Coder/eval/Tester поверх первого.
3. Полный batch-eval не требуется для этой задачи (код экстракции не
   меняется), но синхронный eval всё равно прогоняется штатным
   `ralph_loop.sh`-циклом после этого коммита — метрики должны остаться
   в пределах шума относительно текущего HEAD (никакого влияния на
   `llm_extract_v2.py` в этом изменении нет).
