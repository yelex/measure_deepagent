# RALPH_PROMPT.md

Этот файл скармливается агенту **целиком, без изменений**, на каждой
итерации Ralph loop. У тебя нет памяти о предыдущих итерациях — весь
контекст восстанавливай из файлов ниже. Не проси у человека уточнений,
работай автономно; если что-то заблокировано — зафиксируй блокер в backlog
и заверши итерацию.

## 0. Восстанови контекст (обязательно перед любым действием)

1. Прочитай `AGENTS.md` и `revision_agent/PROGRAM.md` — конвенции и история.
2. Прочитай `IMPROVEMENT_BACKLOG.md` — список задач с приоритетами и
   статусами (`todo` / `in_progress` / `blocked` / `done` / `reverted`).
3. Прочитай последние 5–10 записей `data/output/tuning_log.jsonl` — текущий
   baseline precision/recall и что уже пробовали.
4. Прочитай `git log --oneline -20` — что менялось в последних итерациях,
   особенно записи вида `ralph: revert ...` — это провалившиеся попытки,
   **не повторяй их дословно**.
5. Если в backlog нет ни одной задачи в статусе `todo` — не выдумывай
   работу вслепую: сначала запусти анализ последних `review_queue.json` /
   `tuning_log.jsonl` на предмет повторяющихся паттернов ошибок
   (phantom measures, конкретное поле, конкретная ЖС) и на основе этого
   сформулируй 1–3 новые задачи в backlog с обоснованием (какой паттерн
   ошибок, сколько раз встретился, где в логах). Это тоже полноценная
   итерация — не обязательно сразу переходить к правке кода.

## 1. Выбери ровно одну задачу

- Бери задачу с наивысшим приоритетом в статусе `todo`.
- Если задача уже помечена `blocked` — не трогай, возьми следующую.
- Не берись за несколько задач одновременно, даже если решение кажется
  очевидным и быстрым. Одна итерация = одно изменение, которое можно
  откатить одним `git revert`.
- Переведи задачу в `in_progress` в backlog прямо сейчас, до начала работы.

## 2. Зафиксируй гипотезу до изменения кода

Прежде чем менять tool/prompt/subagent, запиши в
`data/output/ralph_iteration_<timestamp>.md`:
- какую задачу берёшь (id из backlog)
- текущий baseline (precision/recall/конкретная метрика из tuning_log)
- гипотезу: что именно меняешь и почему это должно улучшить метрику
- как будешь проверять (какой eval-скрипт, на каком наборе мер)

Без этого файла итерация недействительна — следующая итерация не сможет
понять, было расхождение в метрике легитимным улучшением или артефактом.

## 3. Внеси изменение

- Правь только то, что относится к выбранной задаче.
- Не трогай `data/output/review_queue.json` и `tuning_log.jsonl` иначе как
  через штатный append (никогда не редактируй существующие записи).
- Не трогай сам eval-скрипт (`scripts/score_against_golden.py`) и эталон
  `docs/меры_автоагент_2.xlsx` **в рамках задачи по улучшению качества**.
  Это не только текстовое правило — `.claude/settings.json` денаит
  Edit/Write на оба файла и на append-only логи на уровне прав, независимо
  от того, что написано в этом промпте. Если задача реально требует
  правки eval-логики — это отдельная задача с явной пометкой
  `eval-change` в backlog, и такая правка требует отдельного ревью
  человеком (не коммить автоматически, оставь как `blocked` с
  комментарием и не продолжай; человеку нужно будет временно снять
  deny-правило вручную).
- Если карточек, которые нашёл агент, но нет в эталоне, накопилось
  несколько — не решай сам, Miss_etalon это или Error_agent (методика
  прямо требует экспертного подтверждения, см. §4). Оставь их как есть:
  `score_against_golden.py` покажет их в `cards_needing_expert_review`, а
  дописывать решение в `data/output/expert_review_overrides.jsonl` — это
  тоже append-only и тоже не твоя работа в рамках обычной итерации
  (только если backlog-задача явно про это).

## 4. Прогони eval

```bash
pyenv exec python3 scripts/score_against_golden.py --agent-export data/output/agent_cards_export.json --note "<backlog-id>: до изменения"
# ... вносишь изменение ...
pyenv exec python3 scripts/score_against_golden.py --agent-export data/output/agent_cards_export.json --note "<backlog-id>: после изменения"
```

**Не используй голый `python3` или `.venv/bin/python`** — на этой машине
Homebrew-сборки Python (3.11/3.12/3.14) имеют ABI-рассинхрон
`pyexpat`/`libexpat` (падает `import openpyxl` и любой `pip install`), а
`pyenv shims` не всегда попадают в PATH автономной сессии. `pyenv exec
python3` явно резолвится в рабочий интерпретатор (pyenv 3.12.0,
openpyxl уже установлен) в обход этой проблемы — см.
`IMPROVEMENT_BACKLOG.md` B006 для полной истории и диагностики.

Выгрузка карточек (`--agent-export`) — JSON-файл, формат которого
зафиксирован в docstring `scripts/score_against_golden.py` (список
карточек по ЖС вбд/сво/инвалиды с полями по образцу колонок эталона). Если
`revision_agent` ещё не пишет такой файл (см. cold-start baseline в
`revision_agent/PROGRAM.md`) — задача про сам экспортёр (B002) идёт раньше
задач по тюнингу, потому что до неё оценивать нечего.

- Сравни новую метрику с baseline из шага 2.
- **Cold-start исключение**: если на момент baseline Recall=0/метрики
  n/a (агент ещё ничего не извлекает), любое движение с 0 (например,
  Match стало > 0 хотя бы на одной ЖС) уже засчитывается как улучшение —
  не жди сразу 0.90 по всем метрикам за одну итерацию.
- Улучшение должно быть измеримым и не должно ронять другую метрику
  (например, +precision ценой -recall — не считается улучшением без
  явного решения человека; в этом случае помечай задачу `blocked`).

## 5. Реши: commit или revert

**Если метрика улучшилась (или как минимум не ухудшилась, а изменение
устраняет конкретный найденный баг):**
- Закоммить с сообщением вида:
  `ralph: <backlog-id> <краткое описание> (precision X→Y, recall A→B)`
- Обнови backlog: статус `done`, добавь фактический результат.
- Допиши запись в `tuning_log.jsonl` с `verdict_detail`.

**Если метрика не улучшилась или ухудшилась:**
- `git revert` или `git checkout` — верни код к состоянию до изменения.
- Обнови backlog: статус `reverted`, обязательно опиши **что именно не
  сработало и почему** (гипотеза была неверной / eval выявил регресс в
  другом месте / и т.д.) — это единственный способ, которым следующая
  итерация узнает не повторять тот же путь.
- Не удаляй сам файл `ralph_iteration_<timestamp>.md` — это тоже часть
  истории экспериментов.

## 6. Жёсткие ограничения на каждую итерацию

- Ровно один backlog-item за итерацию.
- Ни одна итерация не должна завершаться без прогона eval — "выглядит
  лучше" не считается результатом.
- Никогда не редактируй append-only логи задним числом.
- Никогда не увеличивай допуски/пороги eval, чтобы задача "прошла" —
  если хочется поменять сам критерий оценки, это отдельная
  `eval-change`-задача с `blocked` и явным флагом для человека.
- Если 3 итерации подряд заканчиваются `reverted` на одной и той же
  задаче — переведи её в `blocked` с пометкой "нужен человек", не пробуй
  четвёртый раз.
- В конце итерации всегда: backlog обновлён, трейс-файл записан, git-статус
  чистый (либо закоммичено, либо откачено — не оставляй грязный working tree).

Заверши итерацию явным сообщением: что сделано, финальный статус задачи,
метрика до/после.
